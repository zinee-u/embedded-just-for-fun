## 1. 요구 조건과 내가 정한 계약

이번 과제는 8비트 CTRL 및 STATUS 레지스터의 값을 이용하여 장치 활성화, 비활성화, 동작 모드 변경, 준비 상태 확인 기능을 구현하는 것이다.

CTRL 레지스터의 bit0은 ENABLE, bits2:1은 MODE, bits7:3은 다른 설정을 나타낸다. STATUS 레지스터의 bit3은 READY를 나타낸다.

각 함수는 다음 조건을 만족하도록 구현하였다.

- `enable()`: 기존 CTRL의 bit0을 1로 설정하며 다른 비트는 보존한다.
- `disable()`: 기존 CTRL의 bit0을 0으로 설정하며 다른 비트는 보존한다.
- `set_mode()`: 기존 MODE 필드인 bits2:1을 새로운 MODE로 교체한다. 이때 ENABLE과 다른 설정은 보존한다.
- `is_ready()`: STATUS의 bit3만 추출하여 숫자 0 또는 1을 반환한다.

기존에 MODE가 `11`이더라도 새로운 MODE로 교체할 수 있도록 구현하였다.

**과제에서 보장한 조건과 선택한 설계**

과제에서는 새로 지정하는 `mode` 인자가 0~2라고 보장한다. 따라서 현재 구현에서는 별도의 범위 검사를 수행하지 않는다.

네 함수 모두 기존 인터페이스를 유지하고, `uint8_t` 값을 입력받아 계산 결과를 반환하도록 구현하였다.

함수 내부에서 실제 하드웨어 주소에 접근하거나 입력값을 저장하지 않는다. 입력은 값으로 전달되며, 계산 결과도 값으로 반환한다. 따라서 호출자가 별도의 출력 버퍼를 제공하거나 함수 내부 메모리의 수명을 관리할 필요가 없다.

이번 과제의 순수 계산 함수에는 실패 반환 규칙이 별도로 정의되어 있지 않다. 보장된 입력 범위 안에서 항상 계산 결과를 반환하는 방식을 선택하였다.

실제 하드웨어 레지스터에 값을 기록하거나 장치의 동작을 제어하는 기능은 구현 범위에 포함하지 않았다.

## 2. 발견한 모든 근본 원인

| 근본 원인 | 실패 입력 또는 상황 | 발생하는 영향 | 수정 방법과 이유 |
|---|---|---|---|
| ENABLE 설정 시 기존 CTRL 값을 무시함 | `enable(0xA8)` | bit0 이외의 기존 설정이 모두 손실됨 | OR 연산과 `0x01` 마스크를 사용해 bit0만 1로 설정 |
| MODE 변경 시 OR 연산만 사용함 | `set_mode(0xAF, 2)` | 기존 MODE에서 이미 1인 비트를 0으로 변경할 수 없어 올바르게 교체되지 않음 | `0x06` 마스크로 기존 MODE를 지운 후 새로운 MODE를 설정 |
| ENABLE 해제 시 CTRL 전체를 초기화함 | `disable(0xAD)` | MODE와 bits7:3의 기존 설정까지 손실됨 | AND 및 NOT 연산으로 bit0만 0으로 설정 |
| READY를 추출하지 않고 STATUS 전체를 비교함 | `is_ready(0x09)` | READY가 1이어도 다른 상태 비트가 설정되어 있으면 0을 반환함 | 오른쪽 시프트와 AND 마스크를 이용해 bit3만 추출 |

### 2.1. enable()의 문제

기존 구현은 입력받은 CTRL 값을 사용하지 않고 항상 `0x01`을 반환한다.

예를 들어 `0xA8`은 이진수로 `1010 1000`이다. 기존 코드에서는 `0000 0001`을 반환하므로 다른 설정이 손실된다.

이를 해결하기 위해 OR 연산을 사용하였다.

`ctrl | 0x01u`

OR 연산은 마스크가 1인 위치의 비트를 1로 만들고 나머지 비트는 기존 값을 유지하므로 ENABLE만 설정할 수 있다.

### 2.2. set_mode()의 문제

기존 코드는 OR 연산을 사용해 새로운 MODE를 설정한다.

그러나 OR 연산은 이미 1인 비트를 0으로 변경할 수 없으므로 기존 MODE에 따라 올바른 교체가 불가능하다.

특히 `set_mode(0xAF, 2)`에서 기존 MODE는 `11`이다. 새로운 MODE인 `10`을 OR 연산만으로 적용하면 기존 MODE의 bit1을 제거할 수 없다.

따라서 다음 두 단계로 수정하였다.

1. `ctrl & ~0x06`으로 기존 MODE 필드를 제거한다.
2. `mode << 1`로 새로운 MODE를 해당 필드에 배치한 후 OR 연산으로 설정한다.

이 방식은 MODE에 해당하는 bits2:1만 변경하며 ENABLE과 기타 설정을 보존한다.

### 2.3. disable()의 문제

기존 구현은 CTRL 전체를 0으로 만든다.

그러나 요구사항에서는 ENABLE만 해제해야 하므로 MODE와 다른 설정을 유지해야 한다.

이를 해결하기 위해 다음 연산을 사용하였다.

`ctrl & ~0x01u`

이 연산은 bit0만 0으로 변경하고 나머지 비트는 유지한다.

### 2.4. is_ready()의 문제

기존 구현은 STATUS 전체를 `0x08`과 비교한다.

그러나 READY의 의미는 STATUS 전체가 아니라 bit3에 의해 결정된다.

예를 들어 `0x09`는 이진수로 `0000 1001`이며 READY는 1이다. 기존 코드는 전체 값이 `0x08`과 다르다는 이유로 0을 반환한다.

이를 해결하기 위해 다음 연산을 사용하였다.

`(status >> 3) & 0x01u`

이 연산은 READY 비트만 추출하므로 다른 비트의 상태와 관계없이 정확히 0 또는 1을 반환한다.

## 3. 내가 이렇게 답변하겠습니다

이번 과제에서 가장 중요한 조건은 기존 레지스터의 설정을 보존하면서 필요한 비트만 변경하는 것입니다.

원본 코드의 `enable()`과 `disable()`은 입력받은 CTRL 값을 제대로 활용하지 않아 다른 설정 비트까지 손실시킵니다. 따라서 OR 연산과 AND 연산을 사용하여 ENABLE 비트만 변경하도록 수정했습니다.

`set_mode()`는 OR 연산만으로 기존 MODE를 새로운 값으로 교체할 수 없다는 문제가 있습니다. 이를 해결하기 위해 기존 MODE 필드를 마스크로 제거한 후 새로운 MODE를 설정하도록 구현했습니다. 이 방법을 사용하면 기존 MODE가 사용 금지 상태인 `11`이더라도 새로운 MODE인 `00`, `01`, `10`으로 교체할 수 있습니다.

마지막으로 `is_ready()`는 STATUS 전체를 비교하는 대신 READY 비트만 추출하도록 수정했습니다. STATUS의 다른 비트가 설정되어 있더라도 READY를 올바르게 판별할 수 있습니다.

이러한 수정은 함수의 인터페이스를 변경하지 않고 비트 마스크와 시프트 연산만으로 구현할 수 있다는 장점이 있습니다.

다만 새 MODE 인자의 범위가 0~2라는 과제의 보장에 의존하므로 범위 밖 입력에 대한 별도 오류 처리 기능은 없습니다.

필수 일곱 입력의 예상 결과를 이진수로 계산하고, 수정한 프로그램을 통해 실제 결과와 비교하는 방식으로 검증했습니다.

## 4. 선택한 설계와 대안

### 사용한 함수 인터페이스와 호출 예시

기존 함수의 인터페이스를 그대로 유지하였다.

```c
uint8_t enable(uint8_t ctrl);
uint8_t disable(uint8_t ctrl);
uint8_t set_mode(uint8_t ctrl, uint8_t mode);
uint8_t is_ready(uint8_t status);
```

호출 예시는 다음과 같다.

```c
uint8_t ctrl = 0xA8u;

ctrl = enable(ctrl);
ctrl = set_mode(ctrl, 2u);
ctrl = disable(ctrl);
```

위 예시는 연속 호출을 설명하기 위한 것으로, 과제의 필수 일곱 입력은 각각 독립적으로 검증한다.

### 선택 근거

8비트 레지스터를 표현하기 위해 `uint8_t` 자료형을 사용하였다.

ENABLE은 한 개의 비트이므로 `0x01` 마스크를 사용하고, MODE는 bits2:1의 두 비트이므로 `0x06` 마스크를 사용하였다.

READY는 STATUS의 bit3에 있으므로 오른쪽으로 세 칸 시프트한 후 최하위 비트만 추출하였다.

### 고려한 다른 방식

비트 필드를 C 구조체로 표현하는 방법도 고려할 수 있다.

하지만 C 비트 필드의 실제 배치 방식은 구현에 따라 달라질 수 있으므로, 이번 과제에서는 비트 마스크와 시프트 연산을 선택하였다.

또한 포인터로 CTRL을 전달하고 원본 변수를 직접 변경하는 방식도 가능하지만, 이번 과제는 전달받은 값을 계산해 반환하는 방식으로 구현하도록 요구하므로 기존 인터페이스를 유지하였다.

### 현재 방식의 단점과 추가 가정

현재 구현은 새로운 MODE가 0~2라는 조건을 전제로 한다. 범위 밖 입력에 대해서는 별도의 오류 처리를 제공하지 않는다.

또한 실제 하드웨어 접근, 읽기 및 쓰기 부작용, 동시 변경, 원자성 등은 구현 범위에 포함하지 않았다.

### 실패한 결과가 새 명령에 사용되지 않도록 한 방법

이번 과제는 2주차 와이퍼 과제와 달리 성공·실패에 따른 명령 생성 기능을 구현하지 않는다.

문제에서 보장하는 입력 범위에 대해 네 함수가 계산 결과를 반환하도록 구현하였다. 따라서 별도의 명령 전송이나 실패 시 명령 차단 기능은 필요하지 않다.

### const와 volatile 선언

실제 MCU의 읽기 전용 STATUS를 표현하기 위한 선언은 다음과 같다.

```c
const volatile uint8_t *status;
```

`volatile`은 하드웨어에 의해 값이 예상하지 못한 시점에 변경될 수 있음을 컴파일러에 알려 준다.

`const`는 해당 포인터를 통해 STATUS 값을 수정하지 못하도록 제한한다.

두 한정자는 모두 포인터 자체가 아니라 포인터가 가리키는 값에 적용된다.

`volatile`이 원자성이나 동기화를 보장하는 것은 아니므로 실제 MCU 환경에서는 별도의 하드웨어 명세와 동시성 조건도 확인해야 한다.

이번 구현은 macOS 호스트에서 순수 계산 함수만 검증하는 것을 목표로 한다.

실제 MCU의 레지스터 주소에 접근하거나 하드웨어 상태를 변경하는 동작은 확인하지 않았다.

또한 실제 하드웨어에서 발생할 수 있는 레지스터 접근 부작용, 동시 변경, 원자성 및 동기화 문제는 검증 범위에 포함하지 않았다.

실제 제품에 적용하려면 해당 MCU의 데이터시트와 레지스터 명세를 바탕으로 추가 검증이 필요하다.
