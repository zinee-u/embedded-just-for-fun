# 3주차 탐사 장치 레지스터 제어

GitHub 아이디: hoonam33

## 요구 조건과 내가 정한 계약

과제의 CTRL 레지스터는 일반 읽기/쓰기 8비트 값이고 STATUS 레지스터는 읽기 전용 값이다. 네 함수는 하드웨어 주소에 접근하지 않고, 전달받은 `uint8_t` 값을 계산해 결과로 반환한다. CTRL의 bit0은 ENABLE, bits2:1은 MODE이며 bits7:3은 다른 설정이다. STATUS의 bit3은 READY다.

- `enable(ctrl)`은 bit0을 1로 만들고 나머지 비트를 보존한다.
- `disable(ctrl)`은 bit0을 0으로 만들고 나머지 비트를 보존한다.
- `set_mode(ctrl, mode)`는 MODE 필드만 `mode` 값으로 교체하고 나머지를 보존한다. 과제에서 유효한 새 `mode`는 0, 1, 2다. 기존 MODE가 3이어도 교체할 수 있다.
- `is_ready(status)`는 bit3을 추출해 숫자 0 또는 1로 반환한다.


## 발견한 모든 근본 원인

| 근본 원인 | 실패 입력 또는 상황 | 발생하는 영향 | 수정 방법과 이유 |
| --- | --- | --- | --- |
| `enable`이 CTRL을 보존하지 않고 상수 `0x01`을 반환함 | `enable(0xA8)` | ENABLE은 켜지지만 bits7:1의 기존 설정이 모두 사라짐 | `ctrl \| 0x01`로 bit0만 설정한다. 이미 켜져 있어도 다른 비트를 보존한다. |
| `set_mode`가 기존 MODE를 지우지 않고 새 값을 OR함 | `set_mode(0xAF, 2)`처럼 기존 MODE가 `11`인 경우 | OR 연산은 기존 1 비트를 0으로 되돌릴 수 없어 MODE가 요청한 `10`으로 교체되지 않음 | 먼저 `ctrl & ~0x06`으로 bits2:1을 지운 다음 `((mode << 1) & 0x06)`을 OR한다. 이로써 해당 필드만 교체한다. |
| `disable`이 ENABLE만 지우지 않고 0을 반환함 | `disable(0xAD)` | ENABLE뿐 아니라 MODE와 다른 설정도 모두 사라짐 | `ctrl & ~0x01`로 bit0만 지운다. |
| `is_ready`가 STATUS 전체가 `0x08`과 같은지 비교함 | `is_ready(0x09)`처럼 READY와 다른 상태 비트가 함께 켜진 경우 | READY가 켜져 있어도 전체 값이 다르므로 0으로 잘못 판정함 | `(status & 0x08) >> 3`으로 bit3만 추출해 0 또는 1을 반환한다. |

## 내가 이렇게 답변하겠습니다

> 이 문제의 핵심 조건은 CTRL에서 요청한 필드만 바꾸고 나머지 비트를 보존하는 것, 그리고 STATUS 전체가 아니라 READY 비트만 읽는 것입니다. 원본 `enable`과 `disable`은 기존의 설정값을 고려하지 않는 값을 반환해 CTRL의 다른 설정을 잃고, 원본 `set_mode`는 기존 MODE를 먼저 지우지 않아 기존 필드에 따라 새 모드값으로 수정하지 못합니다. 초안의 `is_ready`함수는 STATUS 전체를 `0x08`과 비교해서 다른 비트가 켜진 경우에는 비교할 수 없습니다. 그래서 각 용도에 따라 마스크를 정의하고 ENABLE 설정, 해제, MODE는 해당 필드를 지운 뒤 새 값을 넣고, READY는 3번째 비트만 남긴 후 시프트로 상태를 추출했습니다. 지정된 7개의 입력을 임시 테스트 프로그램으로 빌드하고 실행했으며, 실제 결과는 모두 예상값과 일치했습니다. 실제 MCU의 레지스터 주소나 타이밍은 이 테스트로 검증하지 않았습니다.

## 선택한 설계와 대안

- 사용한 함수 인터페이스와 호출 예시: 기존 함수 원형을 유지했다. 예를 들어 `set_mode(0xAF, 2)`는 `0xAD`를 반환하고, `is_ready(0x09)`는 `1`을 반환한다.
- 선택 근거: 함수에 레지스터 값을 입력하고 변환 결과를 반환하는 단순 계산 방식으로, 과제에서 요구한 비트 동작을 연산을 통해 원하는 비트만 변경하거나 추출할 수 있음.
- 고려한 다른 방식: 연산 시, hex값을 사용하여 연산의 직관성을 높일 수 있었으나 가독성의 편의를 위해 마스크를 정의 후 사용
- 현재 방식의 단점과 추가 가정: `mode`값 입력에 대한 범위 검사는 하지 않는다.
- 실패한 결과가 새 명령에 사용되지 않도록 한 방법: 해당없음.

### 하드웨어 상태를 읽는 선언

`volatile`과 `const`를 통해 프로그램 코드에서 값이 바뀌지 않도록 하고 컴파일러가 일반 값처럼 캐시하지 않도록 한다. volatile의 의미는, 이 값은 프로그램 코드가 바꾸지 않아도 하드웨어에 의해 언제든 바뀔 수 있으니, 컴파일러가 값을 임의로 캐싱하거나 읽기를 생략하지 말고 실제 메모리에서 읽으라는 의미이다.

또한 컴파일러 최적화와 메모리 접근에 관한 키워드이기 때문에 원자성이나 동기화를 보장하지는 않음.

## 실제 실행 환경

- OS 및 CPU 또는 MCU: Windows 호스트. 컴파일러 타깃은 `x86_64` MinGW-w64이며 실제 CPU 모델은 확인하지 않았다. MCU에서는 실행하지 않았다.
- 컴파일러와 버전: GCC 8.1.0 (MinGW-w64).
- 언어 버전과 옵션: C11, `-std=c11 -Wall -Wextra -Wpedantic`.
- 타입 크기 및 타깃과의 차이: 사용한 `uint8_t`는 정확히 8비트인 부호 없는 정수 타입이다. 검증은 64비트 호스트 컴파일러로 했으며 MCU의 ABI나 주변장치 접근 특성은 검증하지 않았다.

## 빌드와 실행 방법

저장소 루트에서 구현 파일만 컴파일해 확인하는 명령은 다음과 같다.

```powershell
gcc -std=c11 -Wall -Wextra -Wpedantic -c submissions/week03/hoonam33/register_control.c -o "$env:TEMP\register_control.o"
```

## 검증 결과

아래 일곱 호출은 각각 독립 입력으로 실행했다. `set_mode`의 새 인자는 과제 허용 범위 안의 2다.

| 입력 또는 시나리오 | 예상 결과 | 실제 결과 | 통과 여부 |
| --- | --- | --- | --- |
| `enable(0xA8)` | `0xA9` | `0xA9` | 통과 |
| `enable(0xA9)` | `0xA9` | `0xA9` | 통과 |
| `set_mode(0xAB, 2)` | `0xAD` | `0xAD` | 통과 |
| `set_mode(0xAF, 2)` | `0xAD` | `0xAD` | 통과 |
| `disable(0xAD)` | `0xAC` | `0xAC` | 통과 |
| `is_ready(0x09)` | `1` | `1` | 통과 |
| `is_ready(0x01)` | `0` | `0` | 통과 |

실행에 사용한 컴파일 옵션은 `-std=c11 -Wall -Wextra -Wpedantic`이며 컴파일 오류나 경고는 없었다. `mode`의 0과 1, 범위 밖 값, MCU의 MMIO 동작, 동시 접근은 미실행이다. 범위 밖 `mode`와 동시 접근은 과제의 보장 조건 밖이므로 이 결과에서 지원한다고 주장하지 않는다.
