# 2주차 와이퍼 센서값 변환 제출 예시

원본 함수의 입력 접근·부호 처리·결과 수명·실패 계약을 함께 수정했습니다. `decode_rain`은 정상 센서값 **0~1000을 값으로 반환**하고, 실패하면 **-1을 반환**합니다. 호출부는 실패를 먼저 확인한 뒤에만 ON/OFF 명령을 만듭니다.

이 제출은 `zinee-u`가 다른 참여자에게 PR 작성 방식을 보여 주기 위해 공개한 예시입니다. 코드를 그대로 제출하기보다 **원인 → 반례 → 설계 이유와 단점 → 실제 검증 결과**의 설명 순서를 참고하세요. 다른 인터페이스도 [과제 조건](../../../weeks/week02/README.md)을 만족하면 가능합니다.

## 요구 조건을 함수 계약으로 정리하기

| 구분 | 계약 |
| --- | --- |
| 입력 | 낮은 바이트부터 오는 부호 없는 16비트 값, 길이가 정확히 2 |
| 호출자의 책임 | NULL이 아니라면 실제로 `len`바이트를 읽을 수 있는 유효한 입력 공간 제공 |
| 입력의 사용 | 호출 중에만 읽고, 수정하거나 주소를 보관하지 않음 |
| 정상 결과 | 0~1000을 `int`로 직접 반환 |
| 실패 결과 | NULL, `len != 2`, 값 > 1000이면 -1 |
| 명령 | 성공한 값이 500 이상이면 ON, 미만이면 OFF |
| 실패 후 동작 | 새 명령 없음. 정상 OFF로 치환하지 않음 |

실제 길이와 다른 길이를 전달하거나 임의의 무효 포인터를 전달하는 호출까지 NULL 검사만으로 방어할 수는 없습니다. 출력 포인터·동적 할당·공유 `static` 결과를 사용하지 않아 결과 저장 공간의 별도 소유권 계약은 필요하지 않습니다.

## 발견한 모든 근본 원인

| 근본 원인 | 문제가 드러나는 상황 | 영향 | 수정과 근거 |
| --- | --- | --- | --- |
| 입력 포인터를 검사하지 않음 | NULL 입력 | `bytes[0]` 접근부터 유효하지 않음 | 첫 검사에서 -1을 반환하고 원소를 읽지 않음 |
| 길이를 전달받지 않고 두 원소를 읽음 | 실제 한 바이트 `{0xF4}` 입력 | `bytes[1]`을 읽을 근거가 없음. 함수 매개변수의 `[]`는 길이를 함께 전달하지 않음 | `size_t len`을 추가하고 정확히 2인지 읽기 전에 검사 |
| 원시 바이트를 signed `char`로 해석 | `{0xF4, 0x01}` 또는 `{0x80, 0x00}` | 낮은 바이트부터 음수로 승격되어 원래 unsigned 값이 보존되지 않을 수 있음 | 입력을 `const uint8_t *`로 받아 0~255로 다룸 |
| 높은 바이트를 부호 있는 값인 채 시프트 | `{0x00, 0x80}` 등 오류 입력 | 높은 바이트가 음수이면 C11의 음수 왼쪽 시프트 문제가 생김. 범위 검사 전에 계산 자체가 잘못됨 | 바이트를 `uint32_t`로 확장한 뒤 이동·조합. 계산 후 캐스팅으로 덮지 않음 |
| 자동 지역변수의 주소를 반환 | `return &rain` 뒤에 호출자가 결과 사용 | 함수 종료 후 객체 수명이 끝나므로 유효한 결과 저장 공간이 아님 | `int` 값 반환으로 바꾸어 지역 주소에 의존하지 않음 |
| 표현 범위와 센서 유효 범위를 구분하지 않음 | 1001 또는 65535 | 정수형에 저장 가능하다는 이유만으로 잘못된 센서값이 사용될 수 있음 | 조합 후 1000 초과를 거부 |
| 성공·실패 및 호출자 사용 규칙이 없음 | 정상 0과 입력 오류를 같은 값으로 처리하는 설계 | 정상 OFF와 변환 실패를 구분할 수 없어 오류가 명령으로 이어질 수 있음 | 정상값과 겹치지 않는 -1을 사용하고 호출부에서 음수 검사를 먼저 수행 |

마지막 항목은 원본에 잘못된 호출 코드가 이미 있었다는 뜻이 아닙니다. 원본 함수만으로는 실패와 호출자의 명령 생성 규칙이 정의되지 않았으므로 이번 제출에서 함께 정했습니다.

### 원본에서 이미 맞는 부분과 별도 검토 사항

- `bytes[0] | (bytes[1] << 8)`의 **낮은 바이트·높은 바이트 위치 자체는 little-endian 순서에 맞습니다.** 바이트 순서가 뒤집힌 코드였다고 분석하지 않았습니다. 문제는 부호·입력 검사 등 나머지 계약입니다.
- `const`는 입력 수정 의도를 제한하지만 길이, 주소 유효성이나 결과 수명을 보장하지 않습니다. `const int *`로 반환형만 바꿔도 지역변수 수명 문제는 남습니다.
- F4를 -12로 해석하는 계산은 **8비트 2의 보수 표현의 예**입니다. 문제의 원문이 모든 정수 표현 방식까지 지정한 것은 아닙니다. 반환 뒤 어떤 쓰레기값이 나온다거나 반드시 충돌한다고 단정하지 않습니다.
- 정상 입력의 높은 바이트는 작아도 잘못된 입력은 `0x80`이나 `0xFF`일 수 있습니다. 거부할 입력을 조합하는 계산도 정의된 동작이어야 합니다.
- 직접 `uint16_t *`로 캐스팅해 읽는 대안은 정렬·접근 타입·호스트 바이트 순서 조건을 추가로 요구합니다. 원본에 없던 결함으로 세지는 않았고, 그런 가정을 추가하지 않도록 바이트별 조합을 유지했습니다.

## 구현이 계약을 지키는 순서

1. `bytes == NULL || len != 2u`이면 배열을 읽기 전에 -1을 반환합니다. 길이 3도 실패이며 부족한 바이트를 임의로 0으로 채우지 않습니다.
2. 각 바이트를 `uint32_t`로 변환한 뒤 높은 바이트를 8비트 옮겨 OR로 합칩니다. 조합 범위 0~65535는 `uint16_t`에 손실 없이 저장할 수 있습니다.
3. 1000 초과는 실패로 처리합니다. 1000으로 보정하거나 정상 0으로 치환하지 않습니다.
4. 검증을 통과한 센서값만 `int`로 반환합니다. 호출자는 반환값을 먼저 `int`에 저장해야 합니다. -1을 `uint16_t`에 먼저 넣으면 오류 판정을 망칠 수 있습니다.
5. `make_wiper_command`는 음수 결과를 `WIPER_NO_COMMAND`로 구분한 뒤 정상값에만 임계값을 적용합니다. `example.c`의 실패 분기는 진단 메시지만 표시합니다.

`F4 01`은 `244 + 1 × 256 = 500`이므로 ON입니다. `E9 03`은 1001이므로 -1과 명령 없음, `F3 01`은 499이므로 정상 OFF입니다. 이미 OFF인 상태에서 499가 다시 와도 정상 OFF 명령은 생길 수 있으며 상태 변화와 명령 생성은 다른 개념입니다.

## 설계 선택과 감수한 단점

| 방식 | 장점 | 비용 또는 주의점 |
| --- | --- | --- |
| **이번 선택인 `int` 값 반환과 -1** | 입력 주소·길이 두 인자로 단순하게 호출. 지역 주소나 출력 포인터를 관리하지 않음 | 모든 호출자가 음수 실패값을 먼저 검사해야 함. 실패 원인은 세분하지 않음 |
| `bool` 상태 반환과 출력 포인터 | 성공 여부와 결과 저장 공간을 분리 | 유효한 출력 객체를 제공해야 하며 실패 시 출력 보존 여부 등 계약 필요 |
| `{ok, value}` 구조체 값 반환 | 상태와 결과를 함께 전달하고 출력 포인터 제거 | 별도 타입이 필요하고 여전히 `ok`를 확인해야 함. 구조체 비용은 타깃별 확인 필요 |
| `static` 결과의 주소 반환 | 지역 자동 변수의 수명 문제를 피할 수 있음 | 호출마다 같은 공간을 덮어쓰며 중첩·동시 호출에서 공유 상태 관리 필요 |
| 동적 할당 결과 반환 | 저장 공간을 함수 종료 후에도 유지 | 할당 실패·해제 책임이 추가되어 이 작은 결과 전달에는 선택하지 않음 |

`uint32_t`는 부호 없는 충분한 계산 폭을 명시하려는 선택입니다. 이 과제의 32비트 `int`에서는 `uint8_t`가 `int`로 승격돼도 최대 `255 << 8`을 표현할 수 있으므로, `uint32_t`를 쓰지 않으면 무조건 틀린 것은 아닙니다. 작은 정수형이 연산 중에도 항상 같은 unsigned 타입을 유지한다고 설명하지 않습니다.

PDF의 32비트 CPU 설명은 타입 선택의 배경으로 참고했습니다. `int`가 언제나 가장 빠르거나, 모든 환경에서 `bool`과 포인터의 크기가 같다는 결론은 내리지 않습니다. 이번 제출에서는 MCU 실행 시간과 구조체 패딩을 측정하지 않았습니다.

명령용 열거형은 PDF의 호출부 조건을 테스트하기 쉽게 함수로 분리한 부분입니다. 이름이 있는 세 가지 결과를 써서 OFF와 명령 없음을 구분하지만, 호출자가 `if (command)`로 판단하면 -1도 참이므로 잘못됩니다. [example.c](example.c)처럼 명령 값을 구분해서 사용해야 합니다.

## 내가 이렇게 답변하겠습니다

> 이 문제는 두 바이트를 합치는 것뿐 아니라 유효한 입력만 읽고, 함수가 끝난 뒤에도 안전하게 결과를 전달하며, 실패한 값으로 명령을 만들지 않는 계약을 정하는 문제라고 보았습니다.
>
> 초안은 NULL과 길이를 확인하지 않고 signed char를 비트 연산에 사용합니다. 또한 지역변수의 주소를 반환하고 유효 범위와 실패 규칙이 없습니다. 저는 입력을 const uint8_t와 길이로 받고, 검사를 통과한 값 0~1000은 int로 직접 반환하며 실패는 -1로 구분했습니다. 바이트를 넓은 unsigned 타입으로 먼저 바꾸어 조합하고, 1000 초과를 거부합니다.
>
> 호출자는 음수를 먼저 검사하고 성공한 경우에만 500 이상인지 판단합니다. 결과값이 복사되므로 지역변수 수명에 의존하지 않고, 출력 포인터의 유효성도 추가로 관리할 필요가 없습니다. 대신 -1 검사 누락을 주의해야 하고 실패 원인을 상세하게 구분하지 않는다는 단점이 있습니다. 아래 검증은 실제로 실행한 호스트 결과이며 MCU 실행 결과와 구분했습니다.

## 재현 방법

다음 명령은 **저장소 루트**에서 실행합니다. 예시와 테스트는 각각 `main`이 있으므로 별도의 실행 파일로 빌드합니다. 모든 `.c`를 한꺼번에 링크하지 않습니다. GCC/Clang 계열과 POSIX 셸 또는 Git Bash의 명령 예입니다.

```sh
mkdir -p build/week02-zinee-u
cc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion \
  -Werror -fsigned-char -O2 \
  submissions/week02/zinee-u/decode_rain.c \
  submissions/week02/zinee-u/example.c \
  -o build/week02-zinee-u/example
./build/week02-zinee-u/example

cc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion \
  -Werror -fsigned-char -O2 \
  submissions/week02/zinee-u/decode_rain.c \
  submissions/week02/zinee-u/tests.c \
  -o build/week02-zinee-u/tests
./build/week02-zinee-u/tests
```

예시 실행의 출력은 다음과 같습니다. 두 번째 줄은 진단 메시지이며 장치 명령이 아닙니다.

```text
ON
DECODE FAILED: no command
OFF
```

AddressSanitizer와 UndefinedBehaviorSanitizer를 지원하는 Clang 환경에서는 다음처럼 검사할 수 있습니다.

```sh
clang -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion \
  -Werror -fsigned-char -O1 -g -fsanitize=address,undefined \
  -fno-omit-frame-pointer -fno-sanitize-recover=all \
  submissions/week02/zinee-u/decode_rain.c \
  submissions/week02/zinee-u/tests.c \
  -o build/week02-zinee-u/tests-sanitized
./build/week02-zinee-u/tests-sanitized
```

## 실제 검증 결과

2026-09-27에 위 명령을 macOS 26.3.1 arm64, Apple Clang 21.0.0에서 실행했습니다. `CHAR_BIT=8`, `CHAR_MIN=-128`, `sizeof(int)=4`, `sizeof(void *)=8`, 고정폭 정수형 크기는 각각 1·2·4바이트였습니다. **호스트의 포인터는 과제 타깃의 4바이트와 다릅니다.**

| 검사 | 실제 결과 |
| --- | --- |
| `-O2`와 엄격 경고 옵션 | 컴파일 경고·오류 없이 빌드, 종료 코드 0 |
| 이름을 붙인 정상·경계·오류 사례 | 20개 통과 |
| 가능한 2바이트 조합 | 65,536개 통과 |
| 정상값 분포 | 0~499의 OFF 500개, 500~1000의 ON 501개 |
| 범위 오류 | 1001~65535의 64,535개를 -1과 명령 없음으로 처리 |
| 입력 보존 | 각 비NULL 사례에서 호출 전후 원본 바이트 일치 |
| 명령 통합 경로 | 각 입력을 이전 OFF·ON 상태 모두에서 검사. 오류는 모의 전송 0회, 정상은 1회 |
| `-O1` 및 AddressSanitizer·UndefinedBehaviorSanitizer | 같은 검사 통과, 진단 없음, 종료 코드 0 |

전수 검사의 예상 센서값은 구현의 시프트·OR 식을 복사하지 않고 `low + high * 256`으로 계산했습니다. 오류 길이는 실제 한 바이트 배열과 세 바이트 배열을 사용했으며, 길이 0은 유효한 버퍼 주소에 처리할 길이 0을 전달했습니다.

대표 사례의 기대값과 실제 검사 결과입니다. 모든 바이트 쌍은 별도 표시가 없으면 길이 2입니다.

| 입력 | 기대 반환값과 명령 | 실제 결과 |
| --- | --- | --- |
| `00 00` | 0, OFF | 일치 |
| `80 00` | 128, OFF | 일치 |
| `FF 00` / `00 01` | 255 / 256, OFF | 일치 |
| `F3 01` | 499, OFF | 일치 |
| `F4 01` / `F5 01` | 500 / 501, ON | 일치 |
| `E8 03` | 1000, ON | 일치 |
| `E9 03` | -1, 명령 없음 | 일치 |
| `00 80` / `FF FF` / `01 F4` | -1, 명령 없음 | 일치 |
| NULL / 길이 0 / 실제 길이 1 / 길이 3 | -1, 명령 없음 | 일치 |

일반 빌드와 sanitizer 빌드의 출력은 모두 다음과 같았습니다. `checks`는 각 사례의 반환값·명령·이전 상태·원본 보존 등 세부 비교를 합친 수이며, 독립 입력 458,894개라는 뜻은 아닙니다.

```text
Host: CHAR_BIT=8, CHAR_MIN=-128, sizeof(int)=4, sizeof(void *)=8, sizeof(uint8_t)=1, sizeof(uint16_t)=2, sizeof(uint32_t)=4
Host results are not measurements of the assignment's 32-bit MCU.
All pairs: 65536; OFF=500 (expected 500), ON=501 (expected 501), NO_COMMAND=64535 (expected 64535), other=0 (expected 0)
PASS: named cases=20, byte pairs=65536, checks=458894, failures=0
```

이전 상태 유지와 전송 횟수는 테스트에서 사용한 모의 호출자 동작입니다. 과제의 필수 조건은 실패 시 새 명령 없음이며, 실제 장치 전송을 수행하거나 측정한 결과가 아닙니다.

## 아직 확인하지 않은 사항

- 32-bit MCU에서의 ABI, 포인터 크기, 코드 크기, 스택 사용량, 실행 시간
- 실제 빗물 센서와 와이퍼 구동부의 통신·전송 실패 처리
- 임의의 잘못된 주소나 실제보다 크게 전달한 거짓 길이 탐지
- 모든 컴파일러·CPU·타이밍에서의 동작에 대한 증명

전수 검사는 길이가 2인 **입력 바이트 값 조합**에 대한 검사입니다. 모든 주소나 호출 조건까지 증명했다는 뜻이 아닙니다.
