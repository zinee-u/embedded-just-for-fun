# 2주차 와이퍼 센서값 변환

GitHub 아이디: LSA31

## 요구 조건과 내가 정한 계약

센서는 부호 없는 16비트 정수를 2바이트 little-endian 방식으로 전달합니다.  
따라서 첫 번째 바이트를 하위 8비트, 두 번째 바이트를 상위 8비트로 조합해야 합니다.

과제에서 주어진 조건은 다음과 같습니다.

- 유효한 센서값은 0~1000입니다.
- 정상 변환값이 500 이상이면 ON, 500 미만이면 OFF 명령을 만듭니다.
- NULL 입력은 실패입니다.
- 길이가 정확히 2가 아니면 실패입니다.
- 변환값이 1000을 초과하면 실패입니다.
- 실패한 입력에서는 새 와이퍼 명령을 만들지 않습니다.
- 함수는 입력을 읽기만 하며 원본을 변경하거나 입력 주소를 보관하지 않습니다.

저는 다음 인터페이스를 선택했습니다.

```c
int decode_rain(const uint8_t *bytes, size_t len);
```

제가 추가로 정한 계약은 다음과 같습니다.

- 성공하면 정상 센서값 0~1000을 `int` 값으로 반환합니다.
- 실패하면 정상 센서값과 겹치지 않는 `-1`을 반환합니다.
- 호출자는 반환값이 `-1`인지 먼저 검사해야 합니다.
- `-1`이면 와이퍼 명령을 생성하거나 전송하지 않습니다.
- 정상값인 경우에만 500을 기준으로 ON/OFF 명령을 만듭니다.

결과를 값으로 직접 반환하므로 함수 내부 저장 공간의 주소를 외부에 전달하지 않습니다.

## 발견한 모든 근본 원인

| 근본 원인 | 실패 입력 또는 상황 | 발생하는 영향 | 수정 방법과 이유 |
| --- | --- | --- | --- |
| NULL 검사 없음 | `bytes == NULL` | 유효한 배열 원소에 접근할 수 없음 | 바이트를 읽기 전에 NULL을 검사하고 실패값 `-1` 반환 |
| 배열의 실제 길이를 전달받지 않음 | 실제 1바이트 배열 | `bytes[1]`이 배열 범위를 벗어날 수 있음 | `size_t len`을 받고, 읽기 전에 `len == 2`인지 확인 |
| 원시 바이트를 signed `char`로 표현 | `80 00`, `F4 01` 등 | `0x80` 이상의 바이트가 음수로 해석될 수 있음 | 입력을 `const uint8_t *`로 변경하여 부호 없는 8비트 데이터임을 명확히 표현 |
| 높은 바이트를 signed 값인 상태에서 왼쪽 시프트 | `00 80`, `FF FF` 등 | 음수 값의 왼쪽 시프트로 정의되지 않은 동작이 발생할 수 있음 | shift 전에 `uint32_t`로 명시적으로 변환 |
| 지역변수 `rain`의 주소 반환 | 함수 종료 후 반환 포인터 사용 | 함수 종료와 함께 객체의 lifetime이 끝나므로 반환된 주소를 결과로 사용할 수 없음 | 포인터 대신 `int` 값을 직접 반환 |
| 센서 유효 범위 검사 없음 | `E9 03`(1001), `FF FF`(65535) | 정수로 표현 가능한 값과 센서에서 허용된 측정값을 구분하지 못함 | 바이트 조합 후 `rain > 1000U`이면 실패 |
| 성공과 실패를 구분하는 계약 없음 | 잘못된 입력을 0이나 OFF처럼 처리하는 경우 | 오류가 정상 OFF 명령으로 이어질 수 있음 | 정상값 0~1000과 겹치지 않는 `-1`을 실패값으로 사용하고 호출자가 먼저 검사 |

원본 코드의

```c
bytes[0] | (bytes[1] << 8)
```

에서 바이트의 위치 자체는 little-endian 순서에 맞습니다.

따라서 바이트 순서를 반대로 사용한 것이 근본 원인은 아니라고 판단했습니다.  
문제는 바이트의 자료형과 부호, 입력 검증, 결과 객체의 lifetime, 성공과 실패의 계약에 있습니다.

## 내가 이렇게 답변하겠습니다

> 이 문제에서 지켜야 하는 조건은 센서가 보낸 부호 없는 16비트 값을 little-endian 순서의 두 바이트에서 복원하고, 0~1000만 정상값으로 인정하며 오류 입력에서는 새 와이퍼 명령을 만들지 않는 것입니다.
>
> 원본 코드는 센서의 원시 바이트를 signed `char`로 받고 실제 입력 길이를 확인하지 않았기 때문에 `0x80` 이상의 바이트를 잘못 해석하거나 배열 범위를 벗어나 읽을 수 있습니다. 또한 함수 내부 지역변수의 주소를 반환하기 때문에 함수 종료 후에는 해당 결과 객체의 lifetime이 끝납니다.
>
> 저는 입력을 `const uint8_t *`와 `size_t len`으로 변경하고, NULL과 길이를 바이트 접근 전에 검사했습니다. 두 바이트는 `uint32_t`로 변환한 뒤 little-endian 순서로 조합하고, 결과가 1000을 초과하면 실패하도록 했습니다. 결과는 지역변수의 주소가 아니라 `int` 값으로 직접 반환합니다.
>
> 정상 센서값이 0~1000으로 제한되어 있기 때문에 이 범위와 겹치지 않는 `-1`을 실패값으로 선택했습니다. 이 방식은 인터페이스가 간단하지만 호출자가 반드시 `-1`을 먼저 검사해야 하고, NULL 오류와 길이 오류처럼 실패 원인을 세부적으로 구분할 수 없다는 단점이 있습니다.
>
> 테스트에서는 0, 128, 255, 499, 500, 1000과 같은 정상·경계값과 1001, 65535, NULL, 길이 0·1·3을 확인했습니다. 또한 입력 원본이 변경되지 않는지, 실패한 입력에서 명령 생성과 전송이 발생하지 않는지도 확인했으며 실행 결과 `Total failures: 0`을 확인했습니다.

## 선택한 설계와 대안

- 사용한 함수 인터페이스와 호출 예시:

```c
int decode_rain(const uint8_t *bytes, size_t len);
```

호출자는 다음과 같이 사용합니다.

```c
int rain = decode_rain(bytes, len);

if (rain == -1) {
    /* 실패: 새 명령을 만들지 않음 */
    return;
}

if (rain >= 500) {
    /* WIPER_ON */
} else {
    /* WIPER_OFF */
}
```

- 선택 근거:

정상값이 0~1000이므로 `-1`을 정상값과 겹치지 않는 실패값으로 사용할 수 있습니다.  
값을 직접 반환하면 출력 포인터, 함수 내부 static 객체, 동적 메모리 할당이 필요하지 않습니다.

- 고려한 다른 방식:

다음과 같이 성공 여부와 결과 저장 위치를 분리하는 방법도 고려할 수 있습니다.

```c
bool decode_rain(
    const uint8_t *bytes,
    size_t len,
    uint16_t *out_rain
);
```

또는 성공 여부와 변환값을 구조체로 함께 반환할 수도 있습니다.

- 현재 방식의 단점과 추가 가정:

`-1` 하나만 사용하므로 실패 원인을 구분할 수 없습니다.  
또한 호출자는 반환값이 성공인지 반드시 확인해야 합니다.

향후 정상 센서값의 범위가 음수까지 확장되는 경우에는 `-1` sentinel 방식의 계약을 다시 설계해야 합니다.

- 실패한 결과가 새 명령에 사용되지 않도록 한 방법:

호출자 역할을 하는 테스트 함수에서 `decode_rain()`의 반환값을 먼저 검사합니다.

```c
int rain = decode_rain(bytes, len);

if (rain == -1) {
    return;
}
```

실패한 경우 이 시점에서 반환하여 명령 생성 함수와 전송 함수를 호출하지 않도록 했습니다.

## 실제 실행 환경

- OS 및 CPU 또는 MCU:
  - Windows 호스트 PC
  - 실제 MCU에서는 아직 실행하지 않음

- 컴파일러와 버전:
  - MSYS2 UCRT64
  - GCC 16.2.0

- 언어 버전과 옵션:
  - C11
  - `-Wall -Wextra -Wpedantic -fsigned-char`

- 타입 크기 및 타깃과의 차이:
  - 과제 타깃의 조건은 `char` 1바이트, `int` 4바이트, 데이터 포인터 4바이트입니다.
  - 현재 호스트 환경의 실제 타입 크기는 아직 별도로 측정하지 않았습니다.
  - 따라서 호스트 PC와 32-bit MCU의 ABI가 동일하다고 가정하지 않았습니다.
